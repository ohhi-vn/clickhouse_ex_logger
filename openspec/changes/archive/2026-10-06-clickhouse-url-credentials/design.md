# Design

## Context

See proposal.md — Why. What constrains the approach:

- **Nothing beneath us accepts a credential.** `AshClickhouse.Repo.config_to_conn_opts/1`
  (deps/ash_clickhouse/lib/ash_clickhouse/repo.ex:167) forwards `:url` and drops
  `:username`/`:password`. `ClickHouse.Interface.HTTP.Client`'s `@opts_schema`
  (deps/clickhouse/lib/clickhouse/interface/http/client.ex:6) has no credential
  key, and `KeywordValidator.validate!/2` rejects unknown keys — so forwarding
  them would raise inside the client, not authenticate.
- **hackney is the only place auth can enter.** `hackney:request/5`
  (deps/hackney/src/hackney.erl:331) reads `#hackney_url.user` and turns a
  non-empty user into `basic_auth`. It `urldecode`s both fields
  (deps/hackney/src/hackney_url.erl:228). So the URL's userinfo is the input, and
  percent-encoding on our side is exactly the inverse of what it will decode.
- **`config/0` is already the single funnel.** `config_to_conn_opts/1` calls
  `repo_module.config()` and nothing else. Every connection — the supervised one
  via `child_spec/1`, the migration's repo connection, and the migration's
  no-database bootstrap connection — is built from that one call.
- **`ClickhouseExLogger.Repo` already overrides `config/0`** to raise on a missing
  or non-keyword configuration, so the composition belongs in a function that
  already exists and already owns this decision.
- **`ipv4_only` round-trips the URL.** `maybe_resolve_ipv4/2`
  (deps/ash_clickhouse/lib/ash_clickhouse/connection.ex:356) does
  `URI.parse(url) |> Map.put(:host, ...) |> URI.to_string()`. `%URI{}` carries
  `userinfo`, so a composed URL survives that rewrite intact.

## Goals / Non-Goals

**Goals:**

- One composition point, so no connection can be built by a path that skipped it.
- Existing hosts see no change on the wire.
- A wrong credential value fails where the host wrote it, not as a delivery
  failure they have to diagnose from a `lost` counter.

**Non-Goals:**

- Changing `AshClickhouse` or `clickhouse` upstream. Both are dependencies; the
  fix belongs here because this is the layer whose documented contract is wrong.
- Supporting authentication schemes other than HTTP basic (mTLS, an external
  secret store). `:ipv4_only` and `:pool_size` pass through untouched.
- A per-request credentials refresh. The URL is read when a connection is
  built, which is when the rest of the connection configuration is read too.

## Decisions

### Compose in `ClickhouseExLogger.Repo.config/0`, not at the call sites

**Chosen:** rewrite `:url` inside `config/0`, which already exists, already
raises on bad configuration, and is already the sole input to
`config_to_conn_opts/1`.

The alternative is a `ClickhouseExLogger.Credentials.compose/1` called from each
of `Application`, `Migration.start_bootstrap_connection/0`, and
`Migration.start_repo_connection/0`. That puts the invariant "no connection is
built without credentials" outside the function that owns configuration, and
makes a fourth call site a future bug.

Rejected: overriding `child_spec/1`. It is generated by `AshClickhouse.Repo`'s
`__using__` and is marked `defoverridable` only for `config/0`, `query/3`, and
`query!/3` — so composing there would mean re-implementing its
`config_to_conn_opts` call, and it would not reach the migration's connections
at all.

### Inject only when a credential is actually configured

**Chosen:** inject when `:password` is a non-empty string, or when `:username` is
present, is a string, and is not `"default"`. A missing username alongside a
non-empty password resolves to `"default"`, which is the name the server's own
default account has.

The alternative the user's own `runtime.exs` workaround uses is "inject only when
the password is non-empty". That is simpler but cannot select a passwordless
non-default user, which is a real shape: a server whose `default` is protected
and whose application account is not. The chosen rule covers it, and matches the
spec's "Username with no password" scenario.

The rule matters most for the hosts already running this library: the documented
configuration is `username: "default", password: ""`, which under this rule
composes to nothing and keeps sending no auth header — byte-identical requests to
today. Any rule that injected on *presence* would silently start authenticating
every existing host, which is a change of behaviour imposed on hosts who asked
for none.

### A URL that already carries userinfo wins

**Chosen:** return it verbatim when `URI.parse/1` reports a non-empty `userinfo`.

The alternative — stripping and re-inserting the configured credentials — would
break every host that has already adopted the `runtime.exs` workaround, which is
precisely the migration path this change is meant to retire. Verbatim also means
this library never has to correctly parse credentials it did not write.

### Validate while composing, and raise `ConfigurationError`

**Chosen:** `config/0` raises `AshClickhouse.Error.ConfigurationError` naming the
offending key, for a non-string `:username`/`:password`, and for a `:url` that does
not not parse into a URL with a host.

The existing `config/0` already raises for a missing key and for a non-keyword
value, and the moduledoc argues why: a silently defaulted destination is the one
outcome this pipeline's other guarantees exist to prevent. A credential dropped
on the floor produces the same class of failure — every request authenticating as
`default` — so it belongs on the same path.

`:url` is checked for a **host**, not merely for parsing. `URI.parse("localhost:8123")`
succeeds and yields `%URI{scheme: "localhost", path: "8123", host: nil}`: the port
is read as a scheme. A parse-success check would accept it and produce a URL
whose host is empty, failing later as an unreachable connection — the exact
misdiagnosis the existing checks exist to prevent.

### Keep the composed URL out of every report

**Chosen:** the composed value is returned from `config/0` and used only to build
connections. No logging, no error message, and no statistics key carries it or any
part of it.

This system reports its own failures through the logger it is logging to, and its
statistics are read by operators. A password in a URL is recoverable in one
`URI.parse`. Existing diagnostics that print a configuration failure —
`ClickhouseExLogger.Repo`'s missing-configuration message, the Mix task's
checklist, `Utils.migrate/1`'s error — already name the config *key*, so they
stay accurate without printing the value.

## Risks / Trade-offs

- **The suite will not prove a server accepts the credentials.** Per the decision
  to leave the shared container password-less, `repo_config_test.exs` covers
  composition, precedence, encoding, and the validation errors; nothing asserts
  that ClickHouse authenticates the result. The residual risk is the dependency
  stack changing how it derives auth from a URL. → Mitigation: the assertion that
  matters is that `config_to_conn_opts/1` forwards our composed `:url` unchanged
  into the client's `:url` option, which is the seam this design depends on. That
  is assertable without a container and is what the test asserts.
- **`URI.encode/2` with `char_unreserved?/1` is stricter than most callers need,
  and stricter than hackney's decoder.** Percent-encoding a character hackney
  would have accepted literally is harmless; the failure mode is the reverse — a
  value encoded too little — which this avoids. → Mitigation: the `@`/`:`/` `/`//`
  and non-ASCII cases are named in the spec and covered by tests.
- **A host that relied on `:username`/`:password` being inert now changes
  behaviour.** A host whose config sets a real password, against a server that
  ignores auth, starts sending an `Authorization` header; a server that rejects
  unknown credentials would now fail where it previously succeeded. → Mitigation:
  this is the change working as specified — those keys were documented as
  credentials. Called out in the README and CHANGELOG as the upgrade note, and
  the URL-with-userinfo escape hatch means a host can always pin the old
  behaviour by embedding the credentials in the URL it already had.
- **`config/0` now does string work on every call.** It is called when a
  connection is built and by `Migration`, never per event or per batch, so this
  is not on the logging hot path. → Mitigation: none needed; noted so it is not
  later "optimized" into the buffer.
